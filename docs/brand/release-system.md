# Release System

![Jinstone conceptual proof frame](./assets/jinstone-proof-frame-v1.png)

One release has one visual thesis and one literal result. Supporting details
can be deep; the cover cannot be vague.

## Required fields

1. Release sequence and date.
2. Literal result or contract change.
3. Evidence level: `FIXTURE`, `HOST`, `BOARD`, `FPGA`, or `SILICON`.
4. Workload and device identity.
5. Baseline and comparison conditions.
6. Commit, artifact digest, or raw-evidence link.
7. Claim boundary.

## Asset matrix

| Surface | Size | Content |
|---|---:|---|
| GitHub organization hero | `1600×640` | Long-term thesis, no release number |
| Social / repository preview | `1280×640` | Product name + one literal offer |
| Release video | `1920×1080` | Six-second identity intro, then product evidence |
| Release cover | `1920×1080` | One result + evidence level |
| Metric card | `1280×720` | One metric, baseline, target, provenance |
| Vertical social | `1080×1350` | Same hierarchy, no additional claims |

## Cover hierarchy

```text
JINSTONE / RELEASE 00N

ONE LITERAL RESULT
IN TWO LINES MAXIMUM

short mechanism or consequence

[EVIDENCE LEVEL]  DEVICE / WORKLOAD / COMMIT / DIGEST
```

## Product footage

The first proof shot should reveal the real object or result: the board,
instrument capture, logic trace, terminal output, report, or integrated action.
Do not lead with abstract animation when a physical artifact exists.

## Publication gate

A release cover is generated only after the evidence bundle exists. A fixture
may be released as tooling, but its cover must remain fixture-colored and may
not use a hardware outcome headline.

Campaign art may establish mood, but the first evidence frame must be a real
artifact, instrument state, report, or completed action. Keep the concept frame
and evidence frame visibly distinct.
